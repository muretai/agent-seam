# The seam — the bytes an implementation must reproduce

**The bytes every implementation must reproduce — and refuse.**

Status: v0. The rules were first written down inside two implementations of them — a JavaScript
door and a Python node — and were extracted on 2026-09-06; since 2026-09-07 this repository
(`agent-seam`) is the home of the contract and of both references, and everything that
reproduces these bytes vendors a pinned copy. The contract belongs to no implementation.
Licence: MIT, the same as the references here. You may implement this seam in any software
under any licence.

This document names what is *pinned*: for each group of the golden vectors
(`vectors/wire_vectors.json`, `vectors/wba_vectors.json`) it states the rule in a few sentences
and names the function that is the reference in each language. It specifies bytes and nothing
else: what an endpoint does with a message it has verified — which routes it serves, what
ladder of checks it runs, what it stores, what it refuses to answer twice — is that
implementation's own business, and one such endpoint is specified in
[`agent-entry/spec/v1.md`](https://github.com/muretai/agent-entry/blob/main/spec/v1.md) §4.
An implementation consumes this contract; it does not extend it.

Two rules apply to every section:

1. **Bytes, not objects.** What is signed or verified is a byte string. Where a rule says
   "canonical JSON", re-serialising a decoded object is never how you verify; you reproduce the
   exact bytes and compare.
2. **Prove your verifier refuses.** An implementation that reproduces every positive vector and
   verifies nothing on receipt authenticates no one. The `reject` groups are not optional.

Vectors are generated by the Python reference (`python/test_wire_vectors.py --regen`,
`python/tools/gen_wba_vectors.py`) and re-derived by every other implementation. The runner
column below says which runner in this repository checks each group today.

## 1. Canonical JSON

The canonical bytes of a JSON value are exactly what Python produces with
`json.dumps(x, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")`:
keys sorted by Unicode code point, separators `,` and `:` with no whitespace, non-ASCII emitted
literally, lowercase `\u00xx` for the control characters JSON must escape and Python's short
escapes (`\n`, `\t`, …) where Python uses them, `/` and DEL unescaped, no Unicode normalisation,
integers bare. `NaN`/`Infinity` are refused.

**Key order is by code point, and only one shape of vector can prove it.** Below U+D800 a
UTF-16 code-unit sort and a code-point sort are the same order, so a group of BMP keys states
the rule and cannot fail: a port sorting the way JavaScript's default `Array.prototype.sort`
does reproduces its bytes exactly. The two orders separate only where an ASTRAL key sits beside
a HIGH-BMP one. `canonical/key-ordering-astral` is that pair — U+1F600 leads with the UTF-16
unit `0xD83D`, which is below U+FFFD's single `0xFFFD`, so a unit sort emits the emoji first
and this contract emits it second — and `canonical/key-ordering-unicode` beside it is the
statement of the rule that a wrong implementation still passes. Both are kept, and the
generator asserts of the astral pair that the two orders actually disagree, because a vector
for an order no pair separates is the defect it exists to close wearing the fix's clothes.

`numberHazards` lists values whose canonical bytes differ between languages (floats). They are
**not** in `canonical` on purpose: a signer must never emit one (`signMustNotEmit`), and a
verifier that meets one may report honestly that it cannot verify that artifact. Every
timestamp in a signed payload is an **integer** epoch second; that is the contract, not a
convenience of the vectors.

### 1.1 UTF-8, and the repair that is not a repair

A canonicaliser MUST refuse a document that is not valid UTF-8, and MUST refuse a string
containing an unpaired surrogate — U+D800–U+DFFF standing alone, whether it arrived as raw bytes
or as a `\ud800` escape, and in a **key** exactly as in a value. `\ud83d\udc26` is a
well-formed pair — high then low, adjacent — so it is one character, U+1F426, and canonicalizes
to those bytes literally; `\udc00\ud800` is two lone surrogates that merely look like a pair,
and is refused. A canonicaliser MUST also refuse a document that carries a **byte order mark**,
and MUST NOT read a document in any encoding but UTF-8 (§1.1.1). `reject.encoding` pins nine such
documents and four that must still render, and it carries every one of them as the **hex of the
raw document bytes**, because a raw invalid byte cannot be written inside a JSON string at all.

The refusal has to happen at the **parse boundary**, before there is a value to inspect, and
this is the part implementations get wrong in the same direction every time. The tempting
behaviour — the default in Go's `encoding/json`, in Node's `Buffer.toString('utf8')`, and in
every decoder documented as "lossy" — is to substitute U+FFFD and carry on. U+FFFD is a
legitimate character that all four references encode happily, so after the substitution nothing
downstream can tell that anything happened: not the canonicaliser, not a UTF-8 validity check
further along, not the verifier.

**A repaired U+FFFD is a different document, and that is the whole vulnerability.** The three
documents `{"s":"\ud800"}`, `{"s":"\udfff"}` and a literal U+FFFD are three documents. After a
repair they are one, and they sign one identical byte string. So a signature made over a message
carrying a literal U+FFFD *also authenticates*, at a repairing receiver, a message carrying
`\ud800` instead — content substitution under a signature that verifies, with nothing failing
and nobody told. That is strictly worse than a message that is rejected. Measured on the pinned
cases: a repairing reader collapses the seven character-level refused documents to four distinct
byte strings, and four of the seven become the *accepted* `literal-replacement-char` document
exactly.

The corollary is that a literal U+FFFD must still canonicalize. It is an ordinary character; it
is the REPAIR that is forbidden, not the code point, and an implementation that refuses U+FFFD
outright has only traded one split for another. `reject.encoding.accept` is that control, and it
also carries one astral character in both of its spellings — as an escape pair and as raw UTF-8
bytes — which must produce identical canonical bytes.

Each reference refuses in its own place, and a port must find the equivalent rather than assume
it inherited one. Python's `json.loads` keeps the lone surrogate in the `str` and
`.encode("utf-8")` raises on it — note that it decodes *bytes* with the `surrogatepass` handler,
so a CESU-8 spelling reaches the encoder rather than the parser: one rule, two doors. Go owns
the boundary itself in `seam.Unmarshal` / `seam.CanonicalFromJSON`, because `encoding/json`
cannot be told not to repair, and a value that has already been through it is unexaminable. Rust
gets both from `serde_json::from_slice`. JavaScript needs two: a **fatal** `TextDecoder` for the
bytes, and `assertEncodable` inside `canonicalBytes` for the escapes, which are pure ASCII and
which no decoder can see.

**Each reference owns the whole boundary in one named function, and a caller uses that function
rather than assembling one.** They are `seam.CanonicalFromJSON` (Go), `canonicalFromJSON`
(JavaScript), `crypto.canonical_from_json` (Python) and `serde_json::from_slice` followed by
`canonical` (Rust). This is a rule about where the guard lives, not a convenience: the recipe
this document used to give JavaScript callers — "a fatal `TextDecoder`, then `canonicalBytes`" —
is wrong, in a way nobody following it could see, and §1.1.1 is what it got wrong.

### 1.1.1 The mark, and the encoding

RFC 8259 §8.1: "Implementations MUST NOT add a byte order mark to the beginning of a
networked-transmitted JSON text." A canonicaliser here MUST refuse one rather than strip it, and
MUST NOT read a document in UTF-16 or UTF-32, marked or unmarked. **The refusal is the same rule
as the surrogates above, one layer out.** `EF BB BF {"a":1}` and `{"a":1}` are two distinct wire
documents; strip the mark and they canonicalize to one byte string, so a signature over either
authenticates the other at a stripping receiver — content its signer never saw, under a
signature that verifies, with nothing failing and nobody told. The pinned pair is
`reject.encoding.refuse/leading-utf8-bom` and `reject.encoding.accept/same-document-unmarked`,
and they exist together because the second is what says the refusal is about the mark and not
about the document.

Measured across the four references before 0.3.1, this split the contract two-and-two. Python's
`json.loads` on *bytes* runs `json.detect_encoding` and read the marked document as `utf-8-sig`;
JavaScript's `TextDecoder('utf-8', {fatal: true})` STRIPPED it, because `ignoreBOM` defaults to
false and the flag means *do not strip*; Go's `encoding/json` and Rust's
`serde_json::from_slice` both refused at the first byte. So Go and Rust already stated the rule
and the other two moved: Python grew `crypto.canonical_from_json`, JavaScript grew
`canonicalFromJSON` with `ignoreBOM: true` and an explicit refusal. The same decision had
already been made once in this family, for the same reason, in agent-entry's
`conformance/receptor-check.mjs`.

Python's boundary was additionally **encoding-autodetecting**: `detect_encoding` reads UTF-16 and
UTF-32, with or without a mark, from NUL bytes in the first four. That is not reachable through
any wire ingress in this repository — `protocol.loads`, `invite`, `jws` and `webbotauth` all
`.decode("utf-8")` explicitly and raise on anything else — but it *was* reachable through the
path this document named, which is the path an implementer copies. `reject.encoding.refuse/
utf16le-no-bom` pins it, and it is a separate case from the mark because it is a separate clause
of the guard.

### 1.2 One name, twice: duplicate keys are last-wins

RFC 8259 §4 says object names **SHOULD** be unique and does not say what happens when they are
not, so every parser picks and no two need pick alike. `{"a":1,"a":2}` is a document a first-
wins reader canonicalizes to `{"a":1}` and a last-wins reader to `{"a":2}` — one wire document,
two signed byte strings, and nothing anywhere reports a problem.

**The rule is LAST-WINS**, pinned by `reject.encoding.accept/duplicate-key-last-wins`, and it
is the rule because it is what all four references were measured doing (Python's `json`,
JavaScript's `JSON.parse`, `seam.Unmarshal`, `serde_json`). The generator asserts that a
first-wins reader over those same bytes produces different canonical bytes, so the case can
actually fail; the port this is aimed at is the fifth one, in a language whose parser picks
the other occurrence or refuses outright, which until now would have signed different bytes in
silence.

**Refusing a duplicate key is the stronger rule, and it is not this contract today.** It is
stronger by exactly the argument §1.1 and §1.1.1 make: `{"a":1,"a":2}` and `{"a":2}` are two
distinct wire documents that collapse to one canonical byte string, so a signature over the
second also authenticates the first at any receiver that reads the raw document with different
duplicate semantics than the canonicaliser did. That is the BOM collision one layer in. It is
not the rule because closing it means a duplicate-detecting parse boundary in four languages —
`object_pairs_hook` in Python and a check in `seam.Unmarshal` are small, a JSON tokenizer in
JavaScript and a custom `serde` visitor in Rust are not — and because it would change what
every consumer's `canonicalFromJSON` accepts. Pinning the agreement the four references already
have is what a vector is for; tightening the rule is a decision with a cascade, and it is
recorded here as open rather than assumed.

## 2. Keys and DIDs

An identity is a 32-byte Ed25519 seed. Its DID is `did:key:z` + base58btc(multicodec prefix
`0xed 0x01` + the 32-byte public key). P-256 keys use their own multicodec prefix and are never
envelope signers. Decoding MUST refuse a wrong multicodec prefix and MUST refuse anything but
exactly 34 decoded bytes; `reject.did` pins both, from the side that can fail.

Both cases there are chosen so that ONE missing check is enough to fail them, because a case two
independent checks both refuse says nothing about either. `x25519-multicodec` is 34 bytes — the
right length, the wrong prefix — so a decoder that only measures accepts it and hands back
somebody's X25519 key as a verification key. `ed25519-prefix-31-byte-key` and
`ed25519-prefix-33-byte-key` are the right prefix and the wrong length, which a decoder that
checks the multicodec and slices `[2:]` returns as 31 or 33 bytes.

**A decoder must also bound how long a base58 string it will look at, and that bound is not a
verdict.** All four references cap it at 512 characters (`MAX_B58_LEN`, `_MAX_B58_LEN`,
`MaxBase58Len`, `MAX_BASE58_LEN`), and no vector pins it, deliberately: no over-long base58
string can decode to 34 bytes — a longer string is a larger integer, and leading `1`s only add
leading zero bytes — so the length rule above refuses every one of them with or without a cap. A
`reject.did` case for it would be green in an implementation that has no cap at all, which is a
check that cannot fail. What the cap buys is CPU. The decode loop is quadratic and it runs on
`from` before any signature is checked, so an unbounded string is unauthenticated CPU exhaustion
at the door every message goes through: measured in Go, 256 KB of base58 costs 1.19 s and 1 MiB
— inside `shared/httputil`'s own `MAX_BODY_BYTES` — costs 13.9 s. (A 400-character DID costs 13
microseconds there and 869 in Rust; the defect is real and further out than it was first
reported to be.) Cost is a property of an implementation, not of the bytes, so it is stated here
and pinned nowhere.

### 2.1 A verification key must be of prime order, and so must `R`

Ed25519's group has a cofactor of 8: eight points sit outside the prime-order subgroup, with
orders 1, 2, 4 and 8. Take the one of order 1 — the identity, encoded `0x01` followed by 31 zero
bytes — and publish it as your `did:key`. It renders as a perfectly ordinary DID:
`did:key:z6MkeXATEjyXENzBXBxgC5EHk2JE5aqd7qMGGtDpLUH1e2Sj`. But verification asks whether
`[S]B == R + [h]A`, and when `A` is the identity, `[h]A` is the identity for **every** scalar
`h`. So `R = the identity, S = 0` satisfies the equation over **any** message. The blob is
`AQAAAA…AA==`: `0x01` then 63 zeros, canonical base64, exactly 64 bytes, structurally perfect in
every respect. The attacker needs no private key and never had one — one DID and one constant
64-byte blob authenticate every message they will ever send, to everyone, forever.

So: a verifier MUST refuse the fourteen small-order encodings, **as the key `from` names and as
the first 32 bytes of the signature**. Fourteen, not eight — seven spellings of `y`, each with
the sign bit clear or set; where `x = 0` the sign bit is a second spelling of one point and a
permissive decoder takes both, and `y = q` and `y = q+1` are the non-canonical spellings of
`y = 0` and `y = 1`. This is libsodium's list. `reject.message/small-order-signer` pins the
identity point and the universal blob; the other thirteen are the same class with more
arithmetic in front of them.

This is not local hardening, it is the contract, because the libraries disagree. RFC 8032 says
it is "sufficient, but not required" to make the strict check, so the permissive equation is a
conforming implementation: Go's `crypto/ed25519` accepts the blob (measured — remove the table
and `reject/small-order-signer` goes green), `cryptography`'s OpenSSL accepts it, and
`ed25519-dalek`'s legacy `verify` accepts it. `node:crypto` refuses it and dalek's
`verify_strict` refuses it. An implementation that accepts what the others refuse is a split in
which **the attacker chooses which implementation reads their message**. So each reference makes
the refusal explicitly: Go `IsSmallOrderPublicKey` / `VerifyingKeyFromDID`, Rust
`is_small_order_public_key` / `verifying_key_from_did` plus `verify_strict`, Python inside
`ed25519_verify` (`_ed25519_wire_ok`, which also covers `R`), JavaScript by inheritance from
`node:crypto`.

Refusing a small-order `R` under an *honest* key is the same rule and is worth stating
separately, because it costs one line and buys non-repudiation: without it the holder of a
private key can mint a second, differently-spelled signature over a message they have already
signed, and both verify. Anything downstream treating the signature bytes as a message's
identity — a dedup key, a replay guard, an idempotency token — is then defeated by the sender.

**And the equation itself is pinned, because refusing the fourteen encodings does not pin it.**
There are two verification equations in circulation and the small-order table is orthogonal to
both:

    cofactorless (RFC 8032 §5.1.7)     [S]B == R + [h]A
    cofactored   (ZIP-215)           [8][S]B == [8]R + [8][h]A

The cofactored form is strictly **weaker** — multiplying through by the cofactor annihilates
any torsion component, so it accepts everything the cofactorless form accepts and more. RFC
8032 calls the strict check "sufficient, but not required", so a port that writes the
cofactored equation is conforming to RFC 8032 and divergent from this wire, and the divergence
is silent: the two differ only on inputs carrying torsion, and every other signature in the
vectors is torsion-free. **A verifier here MUST use the cofactorless equation.**

`reject.message/torsion-cofactored-only` is the case that can fail, and it is closable by a
vector — it does not need a spec sentence alone. Publish `A = A0 + T`, where `A0 = [a]B` is an
honest public point and `T = (0, -1)` is the point of **order 2**. `A` then has order `2l`: it
is MIXED order, not small order, so it is not in the fourteen-entry table and no small-order
check refuses it, and the `did:key` codec spells it like any other key. Sign with the honest
secret and the honest RFC 8032 nonce but over `A`'s encoding — `R = [r]B`,
`h = H(R ‖ enc(A) ‖ M) mod l`, `S = r + ha` — and then

    [S]B = R + [h]A0 = R + [h](A - T) = R + [h]A - [h]T

so the residual is exactly `-[h]T`. Multiply by 8 and it vanishes, because `T` has order 2: the
cofactored equation holds for every `h`, and the cofactorless one holds only when `[h]T` is the
identity, i.e. only when `h` is even. The single condition the case needs is an **odd h**, which
the generator grinds the `messageId` for and then asserts — with an even `h` the signature is
simply valid and the vector would be a check that cannot fail. It also asserts that neither `A`
nor `R` is in the small-order table, that `S` is a canonical scalar and that the base64 is
canonical, so that nothing but the equation can be what refuses the message. All four
references refuse it today: `node:crypto` and `cryptography` through OpenSSL, Go's
`crypto/ed25519`, `ed25519-dalek`'s `verify_strict`, and Python's pure backend, whose last line
is literally `[S]B == R + [h]A`.

**The codec is not where this belongs, and the `did` group proves it.** `did` still round-trips
`publicHex` `0000…0000` (a point of order 4) and `ffff…ffff` in all four implementations, and
must keep doing so: the codec's job is to spell anything a DID can say, and a `did:key` parser
that refuses these would disagree with every other `did:key` parser in the world. The refusal
belongs at the one door from a DID to a key that is about to answer a signature question, which
is why that door has its own name in Go and Rust.

## 3. The signing envelope (the six fields)

The signed payload is the canonical JSON of exactly six fields — `contextId`, `from`,
`messageId`, `text`, `timestamp`, `to` — and nothing else. `contextId` is JSON `null` when there
is no conversation yet; it is still one of the six and still signed. `sig` is base64 (standard
alphabet, padded) of the 64-byte Ed25519 signature made with the key that `from` names. A
verifier derives the public key from `from`, never from anywhere else, checks that `to` names
itself, and refuses a missing field, a wrong recipient, a signature under another key, a
tampered field, and a non-integer timestamp. Freshness (±300 s) and replay (600 s) are the
door's checks, on top of this.

### 3.1 `sig` has exactly one spelling

`sig` is standard-alphabet base64 (`[A-Za-z0-9+/]` with one or two trailing `=`), its length is a
multiple of 4, and — the rule nobody expects — **the decoded bytes must re-encode to the exact
string that arrived**. All three tests, in that order, on every base64 field this contract
compares by identity. The decoded length (64 for a signature) is checked separately, by the
verifier, so that the spelling rule stays about spelling.

The alphabet test alone looks total and is not, which is the trap this rule exists to close. A
64-byte signature is 88 characters ending `==`: 86 data characters carrying 516 bits for 512
bits of signature, so the **final data character holds six bits of which a decoder reads two and
discards four**. All sixteen characters sharing those top two bits decode to the identical 64
bytes. `…BQ==` through `…Bf==` are ONE signature under SIXTEEN names, and every one of them
passes the alphabet test, passes the length test, and is accepted by
`base64.b64decode(validate=True)`, by Go's `StdEncoding`, and by every other decoder — because
they all check the alphabet and none of them checks the residual. One `=` discards two bits: a
family of four. The base64url sibling has the same hole in the same place: a 32-byte key is 43
characters, 258 bits carrying 256, so a JWK `x` has FOUR names (`jws.unb64url`, `strictB64Url`).

Two things follow. A receiver that de-duplicates, logs, replay-caches or indexes on the literal
`sig` string sees sixteen messages where there is one, and fifteen of the sixteen are
respellings anybody can produce without touching a key. And two implementations that both
"validate base64" can disagree about what arrived, which is the shape every signature-stripping
trick is cut from. `reject.message/sig-not-canonical-base64` is a trailing-bit sibling of a
genuine signature — same 64 decoded bytes, one character different in the last data position —
and it is the case in that group that looks completely well-formed, because it is.

The cost is nothing. Every encoder ever written puts zeros in the discarded bits, so everything
an honest signer produced round-trips unharmed and no golden vector moves; only a hand-edited
residual fails, which is precisely the input that had no honest way to exist. The helpers are
JavaScript's private `strictB64`, `crypto.b64_strict` in Python, Go `DecodeSignature`, Rust
`decode_signature`, and whichever is more permissive becomes the split, so all four spell the
rule out rather than delegating it to a decoder.

**Why this rule is for base64 and not for `did:key`.** base64 has a degeneracy base58 does not:
the trailing bits of a padded string are unconstrained, so one byte string has a family of
names. `did:key` is base58 over a big integer, unique once the byte length is fixed — and the
decoder fixes it at 34, with a leading `0xed` that can never be a leading zero byte, so no
leading `1` survives either. Measured rather than assumed: 2798 alternate spellings of one DID
(every single-character substitution, every insertion at each end, one to three leading `1`s)
and not one of them decoded to the same key. The rule is drawn where the degeneracy is.

### 3.2 The recipient is named by the caller, never by the message

A verifier is told who it is; it does not ask the envelope. `to` is one of the six signed
fields, and the check is `to == the recipient the CALLER named`. An implementation that, when
its caller names nobody, falls back to a recipient carried **by the message** compares the wire
against itself: `to == recipientDid` is true for every message ever minted, the signature check
that follows passes because the signature really is valid, and every message addressed to
anybody is accepted by everybody. `reject.message/wire-names-its-own-recipient` is a valid
envelope addressed to a real recipient, replayed with an unsigned `recipientDid` field equal to
`to`, at a verifier that names no recipient of its own — and the JavaScript reference answered
`true` to it until this round (`opts.recipientDid ?? opts.me ?? fields.recipientDid`).

A caller that knows no recipient gets a refusal, not a guess: JavaScript's `verifyEnvelope`
refuses a null recipient before it looks at the signature, and Go's and Rust's `Verify` refuse
an empty `recipientDID` rather than substituting `e.To`. Python cannot express the defect at
all, and that is the design worth copying: `verify_envelope` takes `to_did` **by name** from the
caller and puts it in the signed payload, so a message addressed to somebody else does not
verify for anyone else, and there is no recipient option to fall back to. Any field named
`recipientDid` on the wire is unsigned decoration; it is not one of the six and must never be
read as one.

## 4. The signed Agent Card envelope

`{v: 1, typ: "agentcard", card, ts, sig}`. `sig` covers the canonical bytes of
`{card, ts, typ, v}` and verifies under `card.did` — so a fetcher holding only a DID can verify
the card it fetched, and nobody can publish under another identity's DID. `ts` is signed as the
wire carries it (an integer; a verifier still reads an older float envelope). Asking for a DID
the card does not name must be refused (anti-substitution). The 6-hour freshness window and
the "sign at most hourly" rule are the door's (v1 §4.3, AE-12/AE-13).

**The signature is the whole artifact, and `reject.cardpub` is what says so.** A signed card is
the only proof that a DID belongs to an origin, and every consumer treats a non-null return as
identity proven — so a verifier that returns the card without checking the signature proves
nothing while looking exactly like one that does. Until 0.3.1 nothing here could tell them
apart: `cardpub` was two positive cases plus an anti-substitution case, and anti-substitution is
a string comparison (`expectedDid != card.did`) that runs perfectly well inside a verifier with
no crypto in it. Measured: `verifyCardEnvelope` cut down to a shape check plus `return card`
kept the JavaScript suite green, and `verify_card_envelope` with its `crypto.verify` removed
kept the Python one green. Three refusals now pin it — a signature with one base64 character
changed (still canonical base64, still 64 bytes, so only the Ed25519 check refuses it), an
envelope signed by a different key under the honest `did`, and a genuine signature over a card
body that was edited afterwards. `expectedDid` is the CALLER's, carried at the top level of the
case, never read out of the envelope.

## 5. Device-key binding v2

`typ: "muretai/devicebinding/2"`. An owner (root) key and a device key each sign the binding
payload — canonical JSON of the binding's fields — so a device can prove it acts for an owner
without the owner's seed leaving the owner. Verification is judged at a stated `now` against
`validUntil`; `bindingV2.reject` lists what must be refused (a foreign device DID, a broken
countersignature, an expired binding, …). The v1 `binding` group is kept for the older payload.

**`expectedDeviceDid` is the anti-copy pin, and it comes from the caller.** A binding is a
public artifact: anyone who has seen one can attach it to their own message and be read as the
owner's account at every receiver. So the caller states which device it believes it is talking
to, and the binding must be about that device — the belt over the piecewise checks. Every case
carries `expectedDeviceDid` at its top level and a runner MUST read it from there and never from
the binding, which is asking the attacker who the attacker is. `bindingV2.reject/
binding-lifted-to-another-device` is the case: the binding is byte-identical to the accepted
`no-expiry` one and only the caller's expectation differs, so its refusal can be nothing but the
pin.

## 6. KeyState v1 and OwnerState

A KeyState (`muretai/keystate/1`) lets a root DID delegate to an inline operational key with an
epoch; `resolveOpDid` returns the operational DID when the state verifies and falls back to
the root otherwise. OwnerState is revocation-only: an owner publishes the device DIDs it has
taken away, never the ones it has; `epoch` is the only ordering signal, strictly greater wins.
Both carry integer `epoch`/`ts`. Unknown top-level keys are ignored by verifiers.

### 6.1 KeyState anti-rollback: a resolver that remembers, or a resolver that can be replayed

`revokedOps` read off the record being judged is **unenforceable**, and an implementation that
does not know this will believe its revocation list does something. The list travels inside the
sender's own KeyState. That record is root-signed and therefore authentic — but authenticity is
not freshness. A thief holding a burned op-key attaches an OLDER, still-validly-signed KeyState
in which that key is not yet revoked, and a resolver with no memory honours it. The list can
only ever incriminate a key its own presenter chose to incriminate.

The same missing memory costs two more. A record at a LOWER `epoch` than one already seen is
accepted as readily as a higher one, so rollback is free. And two records at the SAME epoch
naming different `opDid`s are both acceptable, so a fork is invisible. Three findings, one bug:
the resolver remembers nothing about this root.

The memory is a **pinned** KeyState — one for this same root that the caller kept from an
earlier, verified contact — and with it the resolver is a ratchet. The rules, which
`reject.keystate` pins case for case:

1. **The pin is verified before it is trusted**, against the root DID, and an INLINE record is
   verified against `checkNow`'s validity window. A pin that was supplied and does not verify is
   a broken store, not a first contact, so it fails closed to the root rather than degrading to
   the unpinned answer the parameter exists to end. An inline record outside its own
   `notBefore`/`notAfter` does not verify, so it delegates nothing and the answer is the root —
   the same verdict, for the same reason, as a record that does not verify at all.
   `reject.keystate.accept/expired-window` and `/not-yet-valid-window` pin the two ends, and
   they are two cases because `now > notAfter` and `now < notBefore` are two comparisons an
   implementation can carry one of. (Until 0.3.1 every record in the group carried
   `notBefore: 0` and `notAfter: null`, so deleting the window check outright left both
   references fully green — this rule was stated here and tested nowhere.)
   The validity *window* is deliberately not applied to the pin: `notAfter` says a record may no
   longer authorize a key, not that we never saw it, and expiring the pin would hand the thief
   his replay back on a clock.
2. **An inline record displaces the pin only at a STRICTLY greater epoch, and only under the
   same `rootKey`.** Equal is not an upgrade, it is a fork — two histories at one epoch — and
   the one we verified ourselves is the one we keep. Identical content makes `>` and `>=` the
   same no-op; differing content is exactly when it matters. (Measured 2026-08-11: pinned
   epoch 1 → op1, and a replayed epoch-1 record naming op0 resolved to op0.) The `rootKey`
   clause is the other half: a genesis key authorizes a KeyState at ANY epoch, so a record
   signed by a stolen genesis key out-epochs an already-pinned root-rotated one. No lineage
   travels inline; a genuine root rotation arrives through a pull and a fresh pin.
3. **The pin's `revokedOps` binds** — the union with the inline one, not the pin alone. The
   pin's half is the half with teeth, because the stranger did not choose it. A burned answer
   falls back to the key the pin still stands behind, and to the root only when that one is
   burned too: the pin is a verified record of this identity and its own op is the best thing
   left in the room.

**`revokedOps` is a LIST, or nothing is burned.** The field is signed, so it is authentic — and
authenticity has never been a statement about types. A stranger holds their own root key, so
they can mint a KeyState whose `revokedOps` is a number, a boolean, a string or an object, and
`verify_keystate` says True to every one of them. What a resolver does next is the contract:

| `revokedOps` | verifies | a resolver that just asks "is the op in it" | required |
|---|---|---|---|
| `5` | yes | Python raises `TypeError`; JS `.includes` is not a function | the op DID |
| `true` | yes | the same | the op DID |
| `"x<opDid>y"` | yes | Python's `in` is a SUBSTRING test → "burned" → root | the op DID |
| `{"<opDid>": 1}` | yes | membership over dict KEYS → "burned" → root | the op DID |

The first two are the worse half: a remotely-mintable, correctly-signed record that turns a
verifier off with an exception, out of a function documented as pure and total. The last two do
not crash — they answer the wrong question, and the answer is "burned", which sends the resolver
to the root DID and kills every message that peer signs with its live op-key. So a resolver MUST
NOT raise on any of them, and MUST treat all four as burning nothing: a burn list you cannot
enumerate is not a burn list. The rule is `is it a list`, not `does membership work` — JavaScript
`Array.isArray(ks.revokedOps) && ks.revokedOps.includes(opDid)`, Python
`isinstance(revoked, list) and op_did in revoked`, and the same shape `ownerstate.is_revoked`
already uses for the same kind of list.

The reverse must keep working, or the rule above is satisfiable by ignoring the field entirely:
a genuine `[opDid]` list really does burn, and a record that burns its OWN `opDid` authorizes
nobody, so it resolves to the root. An empty list burns nothing. `reject.keystate.accept` pins
all six — the four wrong types, the empty list and the genuine one — and the four wrong-typed
cases carry `mustNotRaise`, because an exception and a wrong answer are different refusals of
this contract and a suite should say which it caught.

The corollary, and the reason `reject.keystate` has an `accept` half: a resolver that always
answered the pin's `opDid` would pass all three refusals and follow nobody's rotation, and a
resolver that ignored its pin argument would still pass first contact. Both are pinned. And
answering the root DID is never a way out — it is safe and it is wrong, because every enrolled
peer's messages then fail as an unknown signer.

The references are JavaScript `resolveOpDid(rootDid, inlineKeystate, now, { pinned })` and
Python `keystate.resolve_op_did(root_did, inline_keystate, pinned_keystate, now=…)`. The
argument ORDER differs, which is why the vector names fields and never positions. The fourth
JavaScript parameter is defaulted rather than a changed signature on purpose: the door splices
that region into its own file verbatim and calls the three-argument form, so a breaking
signature would land a new definition beside an unchanged call — `now` read as a pinned
KeyState — with every test in both repositories still green. Where the pin STORE lives is the
door's decision, not the wire's; every caller passing three arguments is on the first-contact
answer, revocation and all, and should say so rather than believe otherwise.

**The root signature is a separate rule from the ratchet, and it needs its own cases.** Every
record in a rollback pair verifies on purpose — the ratchet is about freshness, not
authenticity — with the consequence that nothing in the group asked whether the root signature
was checked at all. It was not: short-circuiting the signature check inside `verify_keystate`
left the Python suite green at 180/180 and short-circuiting it inside `verifyKeystate` left
`js/conformance/run.mjs` green at 118/118, both measured on 0.3.1. The one guard deciding
whether a KeyState was minted by the identity it names was deletable by the suite's own
measure. Three cases close the three doors an unsigned record comes through:
`inline-signature-forged` (the record the sender attached), `pin-signature-forged` (the record
the caller kept), and `unverified-root-rotated-pin`.

The third is its own rule. A **root-rotated** KeyState — `rootKey` != the DID's own key — is
authorized by a LINEAGE, and the resolver has no lineage parameter, so it cannot judge one and
must not refuse it merely for that. Python declined to judge them and therefore declined to
check anything at all about them, which is not the same set: `rootKey: "dede…de"` is not a
rotation, it is 32 bytes of nothing, and it took the same branch. Measured on 0.3.1, Python's
`resolve_op_did` answered the stranger's `opDid` for that pin where the JavaScript twin
answered the root — one wire, two references, opposite answers, and no vector could see it.
The rule: **a root-rotated pin must still be signed by the `rootKey` it claims**, which every
genuine one is (each link of a root lineage is required to be) and which no forged one can be.
Its lineage remains the store's business.

Go and Rust implement no KeyState. Their runners **skip this group by name and print the skip**,
asserting only that the group is present and non-empty, because a group nobody loops over is
carried in the file and checked by nobody and looks exactly like a group that passes.

## 7. Domain linkage (DIF)

A compact JWS, header `{alg: "EdDSA", typ: "JWT", kid: "<did>#<multibase>"}`, base64url
**unpadded** (a padded or standard-alphabet spelling is refused, not repaired). The signature
covers the text of the first two segments; `signingInput` in the vector is that byte string.
`nbf`/`exp` are integer epoch seconds and `exp` is mandatory: a domain is leased, not owned.

## 8. Web Bot Auth (RFC 9421 subset), verify side

A request carries `Signature-Input`, `Signature` and `Signature-Agent` (an sf-string, quotes
included, also a covered component). `alg` is the lowercase `ed25519` of RFC 9421, not JOSE's
`EdDSA`; `keyid` is the RFC 7638 JWK thumbprint; `tag` names the direction and is inside the
signed parameters; the signature base is LF-joined with no trailing newline; `@authority` is
covered so a signature cannot be replayed at another origin. Verifier inputs are `authority`,
the `jwks` and `now`; `created` may be at most 300 s ahead, `expires - created` at most 600 s.
`wba_vectors.json` pins 5 accepted requests (each to its DID) and 25 that must be refused.
Its `jwks` holds one readable key and TWO entries whose `x` is spelled wrong — one laced
with whitespace, one a trailing-bit sibling (§3.1). Both requests signed under those keys
are otherwise perfect, down to a real RFC 7638 thumbprint as `keyid`, so a reader that
repairs an `x` accepts them; a JWK `x` has exactly one spelling, or a key has many names in
the one document whose whole job is naming keys.

## 9. Cryptobox

X25519 from the seed, HKDF-SHA256, ChaCha20-Poly1305, a 12-byte nonce, base64 of
`nonce ‖ ciphertext`. Only `open` is pinned: `seal` draws a random nonce and is not
reproducible, so a client proves that direction with its own round trip. The direction that
matters is that a client can **open what core sealed**, with the associated data it was sealed
under.

The associated data is **part of the box**. `ad` is authenticated but not encrypted, so it never
appears in the ciphertext and a blob sealed under one `ad` is byte-identical in length, framing
and alphabet to a blob sealed under another: there is nothing in it to look at. The AEAD tag
covers `ad`, so opening under the wrong value is an **authentication** failure, not a decode
failure — the implementation's no-plaintext answer (`None` / `null`), never a partial read and
never a throw. Both directions are pinned: `cryptobox.open` carries one blob with a non-empty
`ad` (`adHex`), and `cryptobox.mustNotOpen` carries the same blob, character for character,
under a different `ad` and under none at all. That second twin is the shape a port actually
ships — `open_box(seed, pub, blob)` with the parameter left off — and it must fail exactly like
a wrong value.

`adHex` is present on **every** case, empty ones included, so that a runner cannot default the
field into existence by forgetting it: an absent key must be an error, because the empty `ad` is
the wrong answer for the one case that has one and would look green. A caller who binds a
contextId and then accepts the box under a different one has bound nothing.

## 10. Relay and invite

`relay` pins the sender-authentication string `to|from|id|blob` (joined with `|`, **not**
canonical JSON) and the listen token over `listen:<did>:<minute>:<origin>`; the origin is the
security field and one relay has one spelling. `invite` pins the signing payload of an invite
card, judged at the case's `checkNow`. Both are Python-only here; the relay's own verifiers
judge a client's bytes in core.

## 11. Security considerations

Two properties of this contract are not defects and cannot be checked by a vector. An
implementation that does not know about them will be wrong in a way its own tests cannot see.

**Resolving a name and connecting to it are two different moments.** Every guard in §7 and in
any URL check answers "is that name safe to dial" at the first moment; the HTTP client resolves
again at the second. A name whose owner controls its DNS can answer differently the second
time, and deciding on one address while connecting to another is the whole of DNS rebinding.
No amount of care in the check closes it. An implementation that must not be rebound has to
carry the **approved address** down to the socket and connect to that, not to the name. Where
redirects are followed, every hop is a fresh decision and must be re-checked; a client that
delegates redirects to its HTTP library has skipped the check on every hop but the first.

**A revocation list is a bounded artifact, so absence from it is not proof.** The OwnerState
record of §6 caps its `revoked` list, keeps the most recently supplied entries and drops the
rest. A revocation that falls off is no longer enforced by a receiver holding only that record:
the disowned device becomes acceptable again. Two rules follow. A tool that MINTS one must warn
as the list approaches the cap — the correct answer at that point is a new owner key, which
invalidates every old binding at once, not a longer list. A tool that CONSUMES one must not
treat "not in the list" as "never disowned"; it is only "not disowned in the window this record
can carry". The same shape applies to any capped list in a signed record.

Both are stated in the reference implementations, at `neturl.py`'s module docstring and at
`ownerstate.py`'s `MAX_REVOKED_DEVICES`.
