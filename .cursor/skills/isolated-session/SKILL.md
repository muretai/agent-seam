# Isolated session

The user types a normal task. Do not wait for a pasted kickoff prompt. Isolate first, then do the work.

## Do this before any file edit

1. Run `scripts/stale.sh`. It exits non-zero when something is past the deadline; deal with those before adding to the pile (see **Deadline**). Its last block is who holds which folder right now.
2. Run `scripts/ensure-worktree.sh` with the user's task as the first argument -- `--design` first when the task is design work (see **Two kinds of session**).
3. Read WORKTREE=, BRANCH= and KIND= from the script output.
4. Edit, test, and commit only inside WORKTREE.

```bash
bash .cursor/skills/isolated-session/scripts/stale.sh
bash .cursor/skills/isolated-session/scripts/ensure-worktree.sh "<user task>"
bash .cursor/skills/isolated-session/scripts/ensure-worktree.sh --design "<user task>"
```

`ensure-worktree.sh` refuses to start when the primary checkout is sitting on a session branch, when BASE and `origin/BASE` have diverged, when the branch it would use already exists without a worktree, or when the folder it would use is **open in another live session**. Each refusal names the fix. Do not paper over one with an override you cannot defend.

## Two kinds of session

- A **dev** session is the default: branch `feat/<slug>`.
- A **design** session -- `--design` -- is for the pages, the theme, the brand copy: branch `design/<slug>`.
- A repository that separates the two lists what design owns in `.cursor/design-paths` (one path per line; a directory prefix ends in `/`). A design session lands only those files; a dev session lands none of them. `finish-worktree.sh` refuses the rest, naming the crossing files. `ISOLATED_SESSION_CROSS=1` lands a crossing change on purpose -- say why in the commit.
- No `.cursor/design-paths` means this repository has no design sessions: `--design` is refused and told to open in the repository that owns the design. In this project that is `muretai-site`; core carries only pinned copies of the design.

## One live owner per folder

Isolation is per folder, not per chat. `ensure-worktree.sh` takes the worktree for this session -- a lock inside the worktree's own git dir, keyed to the chat's owner -- and a second chat asking for the same folder is refused, naming the first. A folder whose owner is gone is taken over with a note. `assert-head.sh` checks the lock before every commit; `stale.sh` lists every holder, with its kind and whether it is alive, GONE, or EXPIRED.

The hook `scripts/session-guard.sh` makes that binding on an editor that never read this file. Claude Code and Claude Desktop run it from `.claude/settings.json`, Cursor from `.cursor/hooks.json`, Grok Build from both:

- **before a file-editing tool** it refuses an edit in the primary checkout, in a folder another live session holds, and in a folder nobody holds -- with the sentence that fixes it;
- **on session start**, when the chat opened a linked worktree directly, it takes that folder (if nobody live holds it) and puts the open-session inventory in front of the chat; when someone does hold it, the chat is told to STOP before its first edit;
- **on session end** it releases every folder this session held.

A launch cannot be vetoed by a hook; the first edit can. That is where a person's second window on the same folder is stopped, whatever they meant to do. `scripts/claim-worktree.sh [path]` takes a free or abandoned folder in place -- never one a live session holds. `ISOLATED_SESSION_GUARD_TRACE=1` in the editor's environment appends one line per event to `<primary>/.git/isolated-session-guard.log` -- how a harness's dialect is verified on its first live chat.

## Harnesses: who the owner is

The owner is a key. For a harness that runs one process per chat it is that process; for one whose chats share a process it is a key the hook reads off its payload and hands to the chat's shells, so the chat's scripts and its hooks agree.

| harness | owner | how the hook is wired | notes |
|---|---|---|---|
| Claude Code (CLI, editor extension) | the chat's `claude` process | `.claude/settings.json` | one process per chat |
| Claude Desktop (Code tab) | the chat's `claude` process | `.claude/settings.json` (Desktop reads project settings for local sessions) | a VM-backed Desktop session reads no project hooks -- and touches no local folder. Desktop's own worktrees under `.claude/worktrees/<name>` are claimable linked worktrees; its GC removes one lock and all, after which the next edit is refused as "no session holds" |
| Cursor Agent mode | `cursor:<conversation_id>` | `.cursor/hooks.json` (camelCase events, `{"permission":"deny"}`) | every chat in a window shares one `agent-exec` process; sessionStart's `env` response gives the chat `ISOLATED_SESSION_OWNER`. A shell that lacks it is told the `export` that fixes it. A key-owned lock also expires after `ISOLATED_SESSION_OWNER_TTL_HOURS` (12) without a `mine` verdict, since a closed chat may send no sessionEnd |
| Grok Build (`grok`, xAI's terminal agent) | the session's `grok` process | reads `.claude/settings.json` and `.cursor/hooks.json` itself (camelCase payload, `{"decision":"deny"}` or exit 2) | project hooks need folder trust once (`/hooks-trust` or `--trust`) |
| Codex, a terminal | the `codex` process / the terminal | no hook here | the scripts bind it: `ensure-worktree.sh`, `assert-head.sh` before every commit |
| Grok Bot (the desktop app with a cloud computer) | its local exec daemon -- one owner for every chat | **none: it reads no hooks** | not guarded (owner decision 2026-09-11). The Bot is instructed to run the scripts; `stale.sh` names it as `grokbot`. Two Grok Bot chats given the same task string would share a worktree |

`iso_harness_keys_shells` in `scripts/lib.sh` is the one-line table of harnesses whose payload id becomes the key; extend it only for a harness that also carries the key into its shells.

## Already isolated?

A codex spawn requires `--cwd` to name a linked worktree: `.git` is a file and
`git -C "$cwd" rev-parse --git-common-dir` resolves. A worktree of another repository
is valid. A primary checkout, its subdirectory, a home directory, `/`, or a plain
directory is refused with exit 2 and one line naming the reason.

Isolated when `.git` is a file (linked worktree), HEAD is not main/master/develop, and the folder's lock is this session's. If you are in the primary checkout, run the script. Do not edit the primary checkout.

Cloud Agent VMs are already isolated. Stay on the `cursor/...` branch. Never push to main.

## HEAD lock

- Do not git switch/checkout away from BRANCH
- Do not git -C into another worktree to commit
- Before every commit and push:

```bash
bash .cursor/skills/isolated-session/scripts/assert-head.sh "$BRANCH" "$WORKTREE"
```

Abort if it fails.

## Finish

When the user's request is done (tests pass, nothing left of the task), merge into BASE. Isolation is for the session, not forever: an unmerged `feat/*` or `design/*` branch means MAIN did not receive the work.

Do not open a draft PR as a substitute for merging. Do not wait to be asked.

1. Commit remaining work on BRANCH only.
2. Confirm HEAD, then merge and delete the session worktree:

```bash
bash .cursor/skills/isolated-session/scripts/assert-head.sh "$BRANCH" "$WORKTREE"
cd "$PRIMARY"   # a call of its own
bash "$PRIMARY/.cursor/skills/isolated-session/scripts/finish-worktree.sh" "$BRANCH" "$WORKTREE"
```

**Run the PRIMARY's copy of `finish-worktree.sh`, by absolute path -- never the worktree's.** The code that judges a landing is BASE's, never the branch's: before it sources anything, the script writes BASE's copy of this `scripts/` directory and of the gate tools (`tools/run_tests.py`, `tools/affected_tests.py`, `tools/sec_lint.py`, `tools/audit_scope.py`, `tools/ledger.py` and the ledger's builders) out of BASE's blobs -- regular files only, so a symlink at a gate path is never followed -- into a private directory (`mktemp -d`, mode 700, removed on exit), and runs THAT copy with the same arguments. So `lib.sh`, `assert-head.sh`, the landing lease (take AND release), the runner (pointed at the branch's tree with `--root`), the ledger check and build, and every step after the fast-forward -- which moves the primary's working tree to the branch's code -- are BASE's. A branch that brings a `tools/ledger.py` BASE does not have gets no ledger run at all. When BASE's gate code cannot be read (no BASE branch, a write that fails) the landing refuses with one line on stderr before any lock, lease or ref is touched. A copy started from OUTSIDE the repository being landed (a vendored skill driving another repository, a test harness) is nothing the branch wrote: when BASE carries no `finish-worktree.sh` of its own, that copy runs, still with BASE's tools; a copy inside the repository with no BASE copy to hand over to is refused. What no code can close: an operator who runs the branch's EDITED `finish-worktree.sh` has handed it control before any line of BASE's runs -- hence the absolute path to the primary's copy (ISSUE(branch-edited-finish-is-trusted-when-run-directly)). `python3 tests/test_finish_base_gate.py` is the contract.

`finish-worktree.sh` is the one serial section of parallel work, so it is short and ordered:

1. it takes the **landing lock** (`<primary>/.git/landing.lock`; one landing at a time; a live holder is waited for up to `ISOLATED_SESSION_LAND_WAIT` seconds, default 2700, a dead one taken over);
2. it **fast-forwards local BASE from `origin/BASE`**, and then **rebases** BRANCH onto that BASE (a branch already on origin -- another laptop's -- is merged, never rewritten; `ISOLATED_SESSION_LAND_MERGE=1` merges too). Origin is the serialization point: two primaries publishing to one origin through their own publishers (`company/ops/publisher/README.md`) means a landing has to descend from what the other one published, or this Mac's publisher holds the hand-off and the next `ensure-worktree.sh` here refuses to start on a diverged BASE. The receipt says which happened -- `BASE_FF=<n> commit(s) from origin/BASE (<old>..<new>)`, `BASE_FF=no-op` when BASE already contains it, `BASE_FF=none (no origin/BASE)` when there is no origin or no such ref. The ff moves a LOCAL ref to a ref that came FROM origin; nothing goes to origin, and the fetch is allowed to fail, because an offline landing is a supported case -- the ff is then judged against whatever `origin/BASE` this repository already has. The ref moves, so the checkout that HAS BASE checked out is brought along, and one holding uncommitted TRACKED changes is refused by name, before anything moves. **So is one where something the incoming commits would CREATE is already on disk** -- ignored or not, a directory where a file would be written included. `git merge --ff-only` refuses only for untracked files it can SEE; an IGNORED one it deletes to make room for the incoming tracked blob, so a commit reachable from `origin/BASE` that tracks `keys/agent-a.key` would take a running node's Ed25519 seed with it -- `keys/`, `data/`, `agents.d/` and `node.env` are ignored here and are that node's live private state inside the primary checkout. The refusal is ours, by name: every colliding path and the checkout it is in, nothing moved, and moving those paths aside is the operator's decision, not the landing's. **Every name printed on an operator's line is spelled out by Unicode CATEGORY** (`iso_safe_text` in `lib.sh`, mirroring `agent/quarantine.py:_visible`): every code point in Cc, Cf, Zl, Zp, Cs, Co or Cn becomes its `\xNN` / `\uNNNN` spelling, so neither `\r` with an erase-line escape nor U+009B (the 8-bit CSI, which is erase-line in a UTF-8 terminal) nor U+202E can repaint the sentence an operator reads immediately before deleting something by hand -- and the path stays identifiable. A byte range would stop at 0x7F; a category does not, and is not an enumeration the next character is missing from. It covers the collision refusals, the `SEC=needs-eyes (...)` file list, the gate-file note, `TESTS_FILES=`, the red-test list, the rebase conflict list, **the lint's findings** (whose `file` and `text` come straight out of the lint, which reads paths as raw bytes) and **the per-test failure tail** (fifteen lines of the branch's own output). **`${branch}` is not on that list, because a branch name that needs escaping is refused instead**, at the very top of the script -- before the landing lock, before `assert-head.sh`, before anything prints -- with the offending code point spelled out: git accepts a C1 byte in a ref name, `${branch}` appears in every refusal, in `BRANCH=`, in the exit notes and in the "waiting for the landing lock" line another operator reads, and a list of sinks is the same shape as the byte range this helper was rewritten to stop being. **And the sanitizer fails closed.** It is asked once, before anything prints: a working python3 is the only answer under which names are printed normally; NO python3 at all falls to the byte-level `tr` and the landing SAYS so (`note: names printed with the byte-level fallback (no python3)`); a python3 that IS on PATH and cannot run refuses the landing, because a fallback weaker than the guard it stands in for may not be chosen in silence. Names are escaped BEFORE they are split into lines -- a hit is one NUL-separated record per thing in the way -- so a name carrying U+000A is one entry spelled `\x0a`, never a fabricated second line in a list whose next sentence is "move those paths aside yourself". **A path component git already TRACKS AS A FILE there is not a collision**: it is git's to replace, so a commit that turns the tracked file `notes` into the directory `notes/` fast-forwards as it should. A tracked DIRECTORY PREFIX is not a tracked file -- `git ls-files --error-unmatch -- ':(literal)keys'` says yes because `keys/README.md` is tracked, and answering the question that way let `git rm -r keys` plus a regular file named `keys` delete the node's key store. So the skip fires only when `ls-files -- ':(literal)<component>'` prints exactly that component, it never applies to the FINAL component, and a symlink is never read as a directory. **What is at the final component decides**: a tracked file there is git's to replace; an untracked or ignored file, or a symlink, is a collision; a DIRECTORY is a collision when anything under it is not tracked (`ls-files --others --exclude-standard` or `--others --ignored --exclude-standard` prints something), named together with a few of the paths under it that would go with it, and lands when every file in it is tracked. An UNTRACKED file in the way of the same incoming `notes/one.md` still is a collision. **"What is there" is the DIRECTORY ENTRY, byte for byte, never a stat of the incoming spelling.** The dev host's filesystem folds case (APFS, `core.ignorecase=true`), so `[[ -d "$root/Keys" ]]` answers about `keys/` while git's pathspec matching stays byte-exact: `ls-files --others [--ignored] -- ':(literal)Keys'` printed nothing and exited 0, the empty answer was read as "every file in it is tracked", and `git merge --ff-only` -- whose own lstat folds too -- landed on `keys/`, unlinked the ignored entries and wrote the file, Ed25519 seed and all. So the walk lists the parent directory and compares the real entry to the component. An exact match keeps the rules above. A CASE VARIANT is git's in one shape only -- a tracked FILE at the final component, which is a case-only rename and is exactly what git fast-forwards correctly -- and is otherwise a collision, refused naming BOTH spellings, the incoming one and the one the filesystem holds, because a refusal that prints only the spelling that is not there sends the operator hunting (and telling them to move a TRACKED file aside trips `is_tracked_dirty` and wedges every later landing). A directory that exists and cannot be listed is a refusal, not a "free". **The check fails closed**: the enumeration of what the range would create runs to a temporary file so `git diff`'s exit status is seen, and a failed enumeration refuses the landing naming that check, instead of concluding from a check that did not run that nothing is in the way. **A TYPECHANGE is judged like an addition.** git's letter for "the same path, a different kind" is `T`, which is neither `A` nor `D`, so a range that flips a tracked gitlink (mode 160000) to a regular blob printed nothing at all for an enumeration asked only about additions and the walk never ran at all. The range is read twice now -- `--diff-filter=A`, walked as before, and the rest of `ACMRDT`, walked by exactly the same rules when the path's current on-disk form can be holding live state -- so what decides is what is on disk, not the letter git chose. **And "can be holding live state" is three shapes, not one**: a real directory, a SYMLINK to a directory (the ordinary arrangement when the state lives on another volume, which `-d && ! -L` refused on both guards, so the walk never ran, `git status --porcelain` said nothing and the merge unlinked the live link), and a CASE VARIANT of the tracked spelling (which `-d` folds into, so the old check answered about the wrong entry and printed a path that, as printed, is not there). An entry that is there and cannot be listed is walked too, and says so. And because `git status` itself FAILS on some of those shapes -- a symlink where a gitlink is tracked is `expected submodule path 'x' not to be a symbolic link` -- the courtesy `git status -sb` inside a refusal can no longer kill the refusal half-written under `set -e`: exit 1 with the landing's own sentence, never exit 128 with a crash wearing a refusal's words. And a tracked GITLINK is the one kind git will not look inside: `git diff`, `git diff --cached` and `git status --porcelain` are all clean however full that directory is, and `ls-files --others [--ignored]` inside it prints nothing, so the walk asks about it directly and `is_tracked_dirty` counts one holding live state as dirty and names it -- a checkout that looks clean and a sentence the operator cannot act on is the failure this replaces. An EMPTY directory has nothing to protect and the same flip lands; a directory that is a checkout of its own (an initialised submodule, or a `.worktrees/<session>` that a `git add -A` staged as a gitlink) is git's own and is not live state. When git refuses for a reason the check did not anticipate, its own message reaches the operator, followed by ours. **The same guard runs at the second sink** (step 7): the branch->BASE merge writes into the primary too, and a session branch that `git add -f`s `keys/agent-a.key`, `node.env` or `data/...` gets past the generated-file check, the tests and the lint. One function, both sinks. **A refusal AFTER the ff says that BASE was moved.** The ff runs before the rebase, the tests, the scan and the merge, so any later refusal exits with `refs/heads/BASE` already advanced and the BASE checkout's tracked files already rewritten from origin -- true of the checkout the operator is sitting in, whatever "the worktree is untouched" says of the session's own. So that exit prints the `BASE_FF=` line on stdout anyway and one sentence on stderr. The two facts it can carry are NOT alternatives, because a landing can have done both: **(i)** the ff moved BASE -- local BASE was moved to `origin/BASE` before this exit (and when nothing had BASE checked out, it says the REF moved and no working tree did, rather than telling the operator their files were rewritten when nothing touched them); this sentence adds *the landing did not happen* only while the merge has NOT run; **(ii)** the merge DID run and a later step failed -- BASE now carries the branch and its tip, permanently, the landing *did not complete*, no receipt was printed, and finish is not to be re-run as it stands; and since the whole receipt block and the whole reviewer section are downstream of the failure, the same sentence says that the landing was `needs-eyes` and owes a review by hand when it was, and that the hand-off was not pushed, so the publisher has not seen that tip. A landing that fast-forwarded AND merged AND then failed prints both (i) and (ii). **(iii)** nothing moved -- nothing is printed. A refusal BEFORE the ff -- diverged, an on-disk collision, a dirty base checkout -- is state (iii). The exit trap releases the landing lock and removes any in-flight temp merge worktree BEFORE it prints, and every print in it is non-fatal, so a stdout that cannot be written to can never leave the lock held by a live pid for the next landing to wait 2700s on. **A diverged BASE stops the landing**: exit non-zero with the real counts (`BASE is A commit(s) ahead of and B behind origin/BASE`), nothing moved -- BASE, the branch and the worktree are as they were and the landing lock is released -- because reconciling two histories is a person's decision. `ISOLATED_SESSION_FORCE=1` lands onto local BASE as before, for the session that is *doing* the reconcile, and the receipt says `BASE_FF=forced (diverged: A ahead, B behind)`. A conflict confined to the generated files (`PLAN.md`, `docs/IMPLEMENTATION_BACKLOG.md`, `docs/SPECIFICATION.md`) is resolved with BASE's copy; any other conflict stops the landing with the steps to resolve it in the worktree;
3. it **refuses a branch that edited a generated file** (`tools/ledger.py check --diff BASE --diff-only`) -- a session writes only its note;
4. it runs **the tests the diff owes** (`tools/run_tests.py --affected BASE..HEAD -j 4`; `ISOLATED_SESSION_LAND_JOBS`); red stops the landing with the red files and their last lines, the worktree left in place, already rebased; `ISOLATED_SESSION_LAND_TESTS=0` skips them and the receipt says so; a test that leaves the tree dirty stops it too;
5. it **scans the diff** (`tools/sec_lint.py --diff BASE..HEAD --json`): `refused` -- a private key, a credential in a known shape, a guard override written into a script -- stops the landing exactly as a red test does, the findings on stderr and the worktree left to fix; `needs-eyes` -- the audited surface or a guard file changed, or a construct a reviewer should see -- lands and owes a reviewer; `clean` owes nothing. **The lint that runs is BASE's**, read out of its blobs (`git show BASE:tools/sec_lint.py`, with `tools/audit_scope.py`) into a scratch directory inside the worktree and removed before the tree is checked again -- never the branch's copy, and never as a fallback when BASE has none (`SEC=none (base has no tools/sec_lint.py)`). And the landing decides one thing itself, from the paths alone: a diff that touches a **gate file** -- `tools/sec_lint.py`, `tools/audit_scope.py`, `tools/ledger.py`, `tools/run_tests.py`, `tools/security_weekly.sh`, `tools/security_daily.sh`, anything under this skill's `scripts/` or `briefs/`, the security-audit skill's `references/`, `.claude/settings.json`, `.cursor/hooks.json` -- is `needs-eyes` whatever the lint said (a `refused` stays refused), those paths go on the reviewer's list, and the receipt line ends in `; gate files changed`. The lint is one of the files on that list, which is why the lint cannot be the one to say so. **`tools/security_daily.sh` is on it because under the `daily` cadence it is the only thing that reviews anything** -- every needs-eyes landing defers to it and the publisher waits for its receipt -- and the table used to name the launchd job and not the script that job runs, so a branch could land an early `exit 0` in it as `SEC=clean`, spawning no reviewer and owing no receipt. It is in `tools/audit_scope.py`'s audited surface for the same reason. Every python the landing runs on BASE's behalf -- this lint, its gate-file table, the generated-file check, the tests harness, the ledger build, the brief render, the summaries -- runs **isolated** (`python3 -I` inside `credless`, which also exports `PYTHONNOUSERSITE=1`): a branch's own test run can write `usercustomize.py` into the user site directory, which is OUTSIDE the checkout and so invisible to the post-test dirtiness check, to the lint and to any reviewer, and every later plain `python3` imports it at start-up. The guards were BASE's for the FILE and not for the INTERPRETER that ran it. **The branch's own test CHILDREN keep the wall, and still find the optional backend** -- which took three goes. `credless` exports `PYTHONNOUSERSITE=1` and a child process inherits an environment variable, so the suites the landing ran could not import an OPTIONAL backend installed in the user site directory (`cryptography`, the relay/E2E layer) and went red inside the landing while passing in the operator's shell. Clearing the variable for them paid that back with the whole hole: `-I` walls only the HARNESS, `tools/run_tests.py` spawns one child per test file with `dict(os.environ)`, and the child's exit code alone decides ok-vs-fail, so one branch test writing `usercustomize.py` with an `atexit` `os._exit(0)` turned every later affected test green for every later landing by any session. So `branch_tests_python` is now the credential wall, `-I` for the harness, `PYTHONNOUSERSITE=1` for the children, and the user site-packages directory in `MURETAI_TEST_BACKEND_PATH`. The runner unsets `PYTHONPATH` for every child and appends that backend directory last in `CHILD_LAUNCHER`, after interpreter startup and the stdlib. `cryptography` remains importable, while a planted `json.py` cannot shadow the stdlib and startup customization in that directory never runs. **And that claim is enforced rather than believed**: `tests/test_gate_pythons_are_isolated.py` greps every `python3` invocation in `finish-worktree.sh`, `lib.sh`, `herd-spawn.sh`, `tools/security_daily.sh` and `tools/security_weekly.sh` and fails on a bare one, because the claim was false one call before the review it protects -- the landing handed `herd-spawn.sh` to a bare `bash`, so the two pythons that decide what the REVIEWER is told and what it may RUN were outside the wall, and the daily engine (the only thing that reviews anything under the `daily` cadence) ran four bare pythons of its own. `credless` is ONE definition, in `lib.sh`, shared by the landing, the daily engine and the weekly clock; the spawner is invoked through it at every caller; and the daily LaunchAgent exports `PYTHONNOUSERSITE=1` itself, so the job carries the wall even when it starts from launchd;
6. it **regenerates the ledgers on the tip** (`tools/ledger.py build`) and commits `ledger: regenerate on landing <branch>` when they changed;
7. it fast-forwards BASE -- guarded on disk exactly as the ff in step 2 is, over `BASE-before..BRANCH` against the checkout it writes into, so a branch that tracks an ignored path the primary holds as live state is refused by name with BASE unmoved -- then removes the worktree (its lock goes with it), deletes BRANCH, releases the landing lock;
8. when the scan said `needs-eyes`, it **spawns the reviewer** -- unless BASE's own `.security/review-cadence`, read from the blob at the sha BASE had BEFORE this landing (`git show <base-before>:.security/review-cadence`) and never from the working tree the merge has just moved to the landed tip, says `daily`, in which case the receipt says `REVIEW=deferred` and `tools/security_daily.sh` (the daily LaunchAgent, `company/ops/launchd/`, 02:00) reads the whole day's range once and writes one receipt for it; `ISOLATED_SESSION_LAND_REVIEW=1` on a landing still spawns one for that landing. A branch that ADDS the cadence file therefore does not defer its OWN review -- BASE did not say `daily` when that landing started -- and a branch that removes it is still deferred, because BASE did; absent in BASE means a reviewer per landing, as before, which is what a vendored copy of this skill with no `tools/security_daily.sh` LaunchAgent needs it to mean. Per landing, when it does spawn: the per-landing brief (`.claude/skills/security-audit/references/landing-review-brief.md`) is rendered with the base sha before the merge, the new tip, the branch and the files to review, written to `~/.cache/muretai-herd/briefs/<name>.md`, and `herd-spawn.sh <name> ... --profile reviewer` starts a session on it (see **Workers through herdr**). The name is `secrev-<20 characters of the branch tail>-<4 of the landed tip>` (32 at most, herdr's bound; unique per landing, so two branches that share a prefix never share a reviewer, a brief or a checkout). The reviewer's cwd is a detached checkout of main as it was BEFORE the landing, `$HERD_DIR/review/<name>` -- OUTSIDE the primary, so the landed tip's `CLAUDE.md` is no parent of it and no session worktree shares its name. The landing removes only what a landing created there: an entry whose physical parent is the physical review root, that git lists as a worktree, whose git dir carries the marker the landing wrote (`muretai-review-checkout`), that is detached, a day old, and held by no live session -- and it walks the review root only after checking that the root is a real directory of ours. `HERD_DIR` defaults to `~/.cache/muretai-herd`, never `/tmp`: Claude Code reads `CLAUDE.md` from the cwd and every directory above it, and `/private/tmp` is world-writable, so a checkout there could be steered by any local uid; the landing and `herd-spawn.sh` refuse a `HERD_DIR` or a cwd with a directory above it that others can write to, and the worker's settings exclude memory files under the temporary directories (`claudeMdExcludes`) as a second layer. A worker obeys the instruction files of its checkout and below, none above: `CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md` and `.claude/rules/` in every directory above its cwd are excluded from memory and denied to Edit/Write, as are the review checkouts, the briefs, the herd's own top-level memory files and `~/.claude/`; auto memory is off (`CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` in the tab, `autoMemoryEnabled: false` in the settings), because it is shared by every session of the repository and written by any of them. A type change is content to the scan (a symlink that becomes a script is a new script), and `AGENTS.override.md` and `.cursor/mcp.json` are gate files. When neither `HERD_DIR` nor `HOME` is set, the landing says `REVIEW=needed` and a spawn exits 2, instead of dying on an unset variable. The landing's gate list is BASE's lint's own table (`tools/sec_lint.py --gate-files`), so there is one table: the whole `.cursor/skills/` tree, `tools/security_weekly.sh` and `company/ops/launchd/` are in it, and an added or type-changed symlink is needs-eyes anywhere, because its target is what runs under the link's name. Since 2026-09-18 an **audit receipt** is in it too: `.security/` is consulted before the record-path rule, so a commit whose only change is a receipt JSON is `needs-eyes` and not `clean` -- nothing signs a receipt, and one landed unread is what let the daily engine be talked out of a whole day (ISSUE(security-audit-2026-09-18-daily-2026-09-18-20)). The receipt's SHAPE rule is unchanged (one regular file, `seq-N/<stamp>-<slug>.json`, never removed, or the landing is refused), and the publisher publishes a records-only commit without waiting for a receipt that could never name it (ISSUE(receipt-needs-eyes-holds-the-publisher)). Herd sessions start with `--strict-mcp-config`: no MCP server reaches them. **The template and the spawner are BASE's too**: `git show <base-before>:<path>` of the template, and of `scripts/herd-spawn.sh` plus `lib.sh` into a temporary directory that is removed after the spawn -- never the primary's working tree, which the fast-forward has just moved to the landed tip, so its copies are the branch's. The render is one pass over the placeholders; the branch name and the file list are data the diff chose, rendered as backticked paths with any backtick, brace pair or newline removed, and the brief says so. The review is non-blocking and runs AFTER the landing; it can neither delay nor fail it. When herdr is absent or down, or `ISOLATED_SESSION_LAND_REVIEW=0`, or BASE had no template or no spawner before this landing, the receipt carries the command to run by hand, because the review is owed either way.

A repository without `tools/run_tests.py`, `tools/sec_lint.py` or `tools/ledger.py` (a pinned copy of this skill) lands as it always did and says `TESTS=none` / `SEC=none` / `LEDGER=none`, with `REVIEW=none`. The receipt carries `BASE_FF=` (`<n> commit(s) from origin/BASE (<old>..<new>)`; `no-op`; `none (no origin/BASE)`; `forced (diverged: A ahead, B behind)`), `REBASED=`, `LANDING_LOCK=waited Ns`, `TESTS=`, `TESTS_SECS=`, `TESTS_FILES=`, `SEC=` (`clean`; `needs-eyes (N file(s) to review: a b c)` -- the audited surface, the guard files and any file that added a construct the lint flags -- with `; gate files changed` before the closing parenthesis when the landing itself forced the verdict; `none (base has no tools/sec_lint.py)`), `LEDGER=`, `HANDOFF=` (`pushed <tip> to <path>` when the primary has a `handoff` remote -- the local bare repository the publisher, another user with the only GitHub token, evaluates and pushes from, see `company/ops/publisher/README.md`; `none (no handoff remote)`; `failed: ...`, never a failed landing), and last `REVIEW=` (`spawned <name> (pane <id>)`; `needed -- run: bash .cursor/skills/isolated-session/scripts/herd-spawn.sh <name> ~/.cache/muretai-herd/briefs/<name>.md --profile reviewer --cwd ~/.cache/muretai-herd/review/<name> --var MAIN=<primary>`; `none`). A `REVIEW=` line is printed whatever happened after the merge -- a checkout that could not be opened is `needed`, never a failed landing. **A refusal over red tests is a receipt too:** stdout carries `MERGED=no`, `TESTS=` with the counted verdict, `TESTS_RED=` with the diff's own red files, `TESTS_COULD_NOT_RUN=` with the suites the room refused (a landing whose runner measured a wall, and whose suite carried the room's refusal in its output -- never a pass, never a red), and `TESTS_REFUSAL=environment|red` (`environment` when only the room refused; `red` when any ordinary red is present; the two lists never name the same file), so a reader sees what the landing measured rather than an empty stdout it has to interpret; the exit status is still the contract, and nothing after the tests ran, so there is no `SEC=` line on that path. A gate file that is deleted, renamed away or turned into a link counts as a gate change (`CLAUDE.md`, `CLAUDE.local.md`, `.claude/rules/` and `.cursor/rules/` are gate files too: every session in the tree obeys them, a reviewer's included), and a branch that removes `tools/sec_lint.py` or `tools/audit_scope.py` is refused before the scan, because the next landing's gate would be `SEC=none`. Abort if it fails. Do not `--force` anything. Report `SEC=` and `REVIEW=` to the owner with the rest of the receipt: a `REVIEW=needed` is a human check they have to see.

**It does not push BASE, and it must not.** No process of the owner's user may hold a GitHub credential, so publishing is not a landing's to do: BASE goes to the local hand-off remote (`HANDOFF=`) and the publisher pushes it. Landing a trunk on the remote is the owner's deliberate act, not a side effect of finishing a session. That is not in tension with the fast-forward in step 2, which moves a LOCAL ref to a ref that came FROM origin. If the receipt says local BASE is ahead of the remote, report that to the owner and let them decide.

**The no-push speed bump, and the wall.** Every session opener (`ensure-worktree.sh`, `claim-worktree.sh`, the session guard's sessionStart) installs `<common git dir>/hooks/pre-push`, which refuses every push unless `ISOLATED_SESSION_PUSH=1` is in the environment; the openers report it as `PREPUSH=installed|present|repaired|replaced|foreign` (`repaired` = a hook carrying our marker but not our body was rewritten; `replaced` = a symlink, FIFO or directory sat at the path; `foreign` = a pre-push hook that is not ours was left alone; a `core.hooksPath` that sidelines it is named, control characters stripped). A session never sets that variable -- `tools/sec_lint.py` refuses the spelling inside any script -- so a push is something the owner types in a terminal: `ISOLATED_SESSION_PUSH=1 git push origin main`. Know what it is: it stops an honest session and a mistake. A same-uid process with code execution can set the variable itself, pass `--no-verify`, or point `core.hooksPath` elsewhere; the wall against that is a push credential no process can use without the owner (an SSH key added with `ssh-add -c`, or no push credential on the box), and the landing runs the branch's tests with git's credential helpers cleared, no terminal prompt, ssh disabled and `gh` pointed at an empty config.

If the user explicitly asked for a PR and not to merge: open a **ready-for-review** PR (not draft) targeting BASE.

Cloud Agent VMs: `finish-worktree.sh` exits 3. Open a ready-for-review PR. Never push to main. A draft PR does not count as finished -- the queue it lands in is nobody's, and it will still be sitting there in a month.

## Deadline

**Seven days. Land it or retire it -- holding is not one of the options.** This applies to a local branch and to an open PR alike. `scripts/stale.sh` is the inventory: unlanded branches with their age, worktrees carrying uncommitted work, who holds which folder, and the open PR queue.

Retiring keeps the history, so it costs nothing:

```bash
git tag archive/<branch> <branch> && git branch -D <branch>
```

Look at the "uncommitted work" block before retiring anything -- that work exists nowhere else.

## Overrides

Each one is a decision you have to be able to defend out loud:

| variable | meaning |
|---|---|
| `ISOLATED_SESSION_FORCE=1` | start anyway on a squatting primary checkout or a diverged BASE, and land onto local BASE when it has diverged from `origin/BASE`. For the session that is *doing* the reconcile. |
| `ISOLATED_SESSION_RESUME=1` | reattach to an existing branch that has no worktree (a killed session). |
| `ISOLATED_SESSION_CROSS=1` | land a design session's change outside its paths, or a dev session's change inside them. Say why in the commit. |
| `ISOLATED_SESSION_TAKEOVER=1` | evict a live session from a folder. Only when that session is yours and idle. |
| `ISOLATED_SESSION_OWNER=<key>` | who this session is: a pid, or a harness key such as `cursor:<conversation_id>` (Cursor's sessionStart hook sets it; the tests use it). |
| `ISOLATED_SESSION_OWNER_TTL_HOURS=N` | how long a key-owned lock stays alive without a `mine` verdict (default 12). |
| `ISOLATED_SESSION_GUARD=off` | switch the hook off for one editor process. |
| `ISOLATED_SESSION_GUARD_TRACE=1` | log every hook event and verdict to `<primary>/.git/isolated-session-guard.log`. |

| `ISOLATED_SESSION_LAND_REVIEW=0` | do not spawn the reviewer after a `needs-eyes` landing. The receipt still says `REVIEW=needed` with the command: the review is owed, you are choosing to start it yourself. |

## Workers through herdr

`scripts/herd-spawn.sh <name> <brief-file> [--cwd DIR] [--profile worker|reviewer] [--env K=V ...] [--var KEY=VALUE ...]` starts one worker session: a herdr tab in a checkout (default: the primary checkout of the repository the script lives in), an interactive `claude` in it -- its own process, so the guard sees it as its own session -- and the brief as its first prompt. `{{KEY}}` placeholders in the brief are filled from `--var`; `{{NAME}}`, `{{PRIMARY}}` (the cwd) and `{{REPORT}}` are filled for you, in ONE pass (a value is substituted, never re-scanned, so a value carrying `{{NAME}}` reaches the worker as literal text); the filled copy is `~/.cache/muretai-herd/briefs/<name>.md`, and a placeholder the template carries that nobody filled stops the spawn (exit 2) rather than reaching a worker as literal braces. What herdr is told to prompt is the text the script rendered, not a re-read of that file. Each worker gets its own directory, `~/.cache/muretai-herd/<name>/`, the only directory added to its session (`--add-dir`), and its report is `~/.cache/muretai-herd/<name>/report.md`; `HERD_DIR` moves `~/.cache/muretai-herd`, which is created mode 700 when absent and refused (exit 2) when it exists and someone else owns it. It exits 3 with one line when herdr is not on PATH or its server is down (`HERD_SPAWN_BIN` names the binary), and on success prints one line: `worker=<name> pane=<id> tab=<id> report=~/.cache/muretai-herd/<name>/report.md`. The worker runs in Claude Code unless `HERD_SPAWN_HARNESS=cursor` names Cursor's CLI agent instead (herdr drives either; the same brief, report directory and receipt tools; the same allow/deny lists written in Cursor's spelling to the workspace's `.cursor/cli.json`, gitignored, plus `Read`/`Write` of the worker's report directory and `Write` of the primary's `.worktrees/`; the model is the Cursor account's default unless `HERD_SPAWN_MODEL` names one). Cursor's CLI runs in the account's **allowlist** mode, never `--auto-review`: measured on 2026-09-12, the classifier mode ran `git push`, `cat` and `curl` past their deny rules, while in allowlist mode a denied command is blocked, an allowed one runs, and an unlisted one waits for a person (the session shows as `blocked` in herdr, the safe failure); the spawn refuses when `~/.cursor/cli-config.json` says another `approvalMode`. Cursor's CLI does run the project's `.cursor/hooks.json`, so the isolated-session guard holds there too (measured: `owner=cursor:<conversation_id>` in the trace). In Claude Code the worker runs on `opus` (`HERD_SPAWN_MODEL` overrides it with an alias or a model id; a reviewer reads for twenty to forty minutes, and on a subscription that is the cost that matters) and in `auto` permission mode (`HERD_SPAWN_PERMISSION_MODE` overrides it with exactly one of `auto`, `acceptEdits`, `manual`, `plan` -- anything else, an empty string included, is exit 2 before herdr is asked anything, and the value is not handed down to the tab, so a session a worker spawns starts from the default again; in `acceptEdits` a worker stops at every command outside the allowlist, and the first real reviewer did). The allowlist names each script by its exact path -- `python3 tools/audit_scope.py`, `tools/ledger.py`, `tools/sec_lint.py`, `tools/affected_tests.py`, `tools/spec_build.py`, `python3 -m agent.plugins` (now shadowed by the shape deny below), these scripts, `cd`, read-only git plus `git add` / `git commit`, `grep` / `ls` / `wc` / `head` / `tail` -- never bare `python3` or a directory prefix (a Bash rule matches the command's PREFIX, so either would run whatever the diff itself landed) and never `cat` (Read is the tool for a file). Each of those is granted in the bare AND the isolated (`python3 -I ...`) spelling, because **the tab itself carries the wall**: `--env PYTHONNOUSERSITE=1` is on the `herdr tab create` call, and every brief instructs `python3 -I`. That `--env` list IS the tab's environment -- `tab create` is an RPC to the herdr daemon, so a `credless` around the spawner walls the spawner's own pythons and reaches nothing the daemon starts, and a live reviewer's `printenv PYTHONNOUSERSITE` exited 1 while its `write-receipt` was the one python in the chain nobody had isolated. A list granting only the bare spelling would stop a worker at a permission prompt on its own instructions, so the tab, the briefs and the rules say the same thing. `--profile worker` (default) adds `python3 tools/run_tests.py` and `python3 tests/test_*` in both spellings; `--profile reviewer` -- what a landing and the weekly clock use -- does not, because a reviewer runs no tests and reads a diff an attacker may have written in full. `git push` is refused by the session's own rule, which is a promise the session keeps, not a guard on the remote. A worker is an interactive session, billed like one. Its rules are a settings file the spawn writes exclusively (`$HERD_DIR/<name>/permissions.json`, O_EXCL, mode 600, in a directory it owns) and loads with `--setting-sources project,local`, so the owner's user-global settings never reach a worker; the deny list names the shell readers and interpreters and `git diff --no-index`. A deny list is not containment (ISSUE(reviewer-sandbox-is-a-denylist)).

**Arbitrary-code python is denied by SHAPE, not by spelling.** The deny list refuses any `python`/`python3` invocation that carries `-c`, `-m` or a bare `-` argument, whatever flags stand between: `python3 -c`, `python3 -m`, `python3 -`, and equally `python3 -I -c`, `python3 -Ic`, `python3 -I -`, `python3 -I -m http.server`, `python3 -I -B -c`, `python3 -u -I -c`. `-c` and `-m` consume the rest of a short-option cluster, so a cluster carrying one ends in `c` or `m`, and that is what the cluster rules read. The rules covered the BARE dialect only until 2026-09-18, and the landing that made `python3 -I` the house form in all six briefs therefore left `python3 -I -c` matching no rule at all -- neither deny nor allow, so it reached the auto-mode classifier, which is the wave-through the list exists to stop (ISSUE(security-audit-2026-09-18-daily-2026-09-18-16)). What keeps working is exactly `python3 -I <path>`, the form the briefs instruct; `test_herd_spawn.test_deny_by_shape` pins sixteen refused shapes and five kept ones against the worker's, the reviewer's and the Cursor profile's own lists. One casualty is named in the rules: `python3 -m agent.plugins` is no longer reachable by a worker (a deny beats an allow), and the plugin check a session reads is the one `tools/security_weekly.sh` already ran.

### The three harnesses

`HERD_SPAWN_HARNESS` picks which agent herdr starts in the pane. The brief, the report
directory and the receipt tools are the same for all three; what differs is **what the wall
actually is**, and that difference is not interchangeable.

| harness | the agent | what the wall is | profiles |
| --- | --- | --- | --- |
| `claude` (default) | Claude Code | the allow/deny lists, as `$HERD_DIR/<name>/permissions.json` | worker, reviewer, coordinator (the only harness that meets the seat) |
| `cursor` | `cursor-agent` | the same lists in Cursor's spelling in `<cwd>/.cursor/cli.json`, allowlist mode | worker. Does not coordinate: no per-pane appl-hook, and it reads rules the spawn does not own |
| `codex` | `codex` (codex-cli) | the SANDBOX (`-s workspace-write`) plus the approval policy (`-a on-request`), and no session guard at all | worker, in a worktree only. Does not coordinate: no per-command deny and no hook |

The coordinator seat is not a harness name. The spawn sits a harness only when it can write
that pane's allow and deny into a file the harness loads alone, and register `appl-hook.sh`
on that pane alone (`UserPromptSubmit` and `SessionStart`), never into the shared project
`.cursor/hooks.json`. Claude meets both: the lists and the hooks live in
`$HERD_DIR/<name>/permissions.json`, loaded with `--settings` and `--setting-sources project`.
Cursor does not coordinate: `appl-hook.sh` has no per-pane slot (the hook is written only
into the claude `--settings` file), `cursor-agent` reads the user's own rules and skills,
and its rules file is `<cwd>/.cursor/cli.json`, which a coordinator would share because its
cwd is the primary. Codex does not coordinate: it has no per-command deny list and no
session-guard hook.

**Codex has no per-command allow/deny list at all.** `Bash(cmd:*)` and `Shell(cmd:args*)`
have no spelling there, so the lists above are **not enforced** on it: `git push`, `curl`,
a read of `keys/` are stopped by the sandbox and by whatever a person answers at an
approval prompt, and by nothing else. `danger-full-access` and
`--dangerously-bypass-approvals-and-sandbox` are never passed. Rather than pretend
otherwise the spawn writes the lists to `$HERD_DIR/<name>/rules.unenforced.json` with a
note saying they are not enforced, writes no `permissions.json` (a rules file the harness
ignores would read as a wall that is not there), and prints one line on stdout saying the
same where the person spawning the worker reads it. For that reason
**codex reviews nothing and coordinates nothing**: `worker` is its only profile, and `--profile reviewer`
or `--profile coordinator` is exit 2 before herdr is asked anything -- a reviewer reads a
diff an attacker may have authored in full, and the deny list it would need does not exist
on this harness. A coordinator is refused for the seat, not with that sentence: no
per-command deny list and no session-guard hook, so `appl-hook.sh` cannot be registered
on that pane alone.

**And no session guard runs on a codex worker.** The isolated-session PreToolUse hook is
registered in `.claude/settings.json` and `.cursor/hooks.json`, `scripts/session-guard.sh`
dispatches claude, cursor and grok only, codex-cli reads neither file, and the `config.toml`
the spawn writes registers no hook of its own -- so the sentence "the hook still refuses the
primary and other sessions' worktrees" holds for two harnesses out of three and not for this
one (ISSUE(session-guard-has-no-codex-dialect)). A codex worker is therefore started with
`--cwd <worktree>` and never in a primary checkout: `-s workspace-write` makes the directory
it opens in its writable sandbox root and `-a on-request` escalates only for writes OUTSIDE
that root, so every write inside runs with no approval and with nothing to refuse
`<primary>/.claude/settings.json`, the landing scripts, `keys/` or another live session's
worktree -- none of which would appear in a diff. Without `--cwd`, or with `--cwd <a
primary>`, the spawn is exit 2 before herdr is asked anything.

Its config home is the spawn's, never the user's: codex loads `AGENTS.md` and `config.toml`
from `CODEX_HOME` (default `~/.codex`), where any session of this user may write, so the
tab is handed `CODEX_HOME=$HERD_DIR/<name>/codex-home` (mode 700; a symlink or another
uid's directory is exit 2 before a tab exists) holding one `config.toml` the spawn wrote
exclusively -- the model, the sandbox mode, the approval policy, nothing else. That home
must hold **nothing the spawn did not just write**: a non-empty one is exit 2 listing what
is in the way (spelled through `iso_safe_text`), refused and never emptied, because a
planted `AGENTS.md` there would be the worker's instructions, in no checkout and in no
diff. A spawn that fails later removes the `config.toml` and the login link it made, so the
retry is not refused by its own leftover, and a home a previous spawn of that name left
refuses the re-spawn exactly as its `brief.md` does. Only the
login crosses over, as a **symlink** to the user's own `auth.json`: the path is handled and
the content never read, printed or copied, and a machine with no codex login is told to log
in rather than handed a pane whose agent cannot talk. That path is judged before it is
linked -- a regular file (`-L` first, then `-f`) owned by the caller (`-O`), under a home
that passes `iso_private_path` -- since `-e` follows a symlink and accepts a directory or a
fifo, and what is linked in is the account the session is billed to. `CODEX_HOME` is read
once, for that login, and then `unset` like `HERD_SPAWN_HARNESS` and `HERD_SPAWN_MODEL`, so
a spawn a worker starts inherits no home it never chose. `HERD_SPAWN_PERMISSION_MODE` is
**refused** on this harness rather than validated and dropped: the approval policy is fixed
at `-a on-request`, and a knob that silently does nothing is the one thing this harness's
whole design is built to avoid. `HERD_SPAWN_MODEL` is passed as `-m`;
unset means the account default (measured 2026-09-20 on codex-cli 0.155.1:
`gpt-5.1-codex-max` is refused for a ChatGPT account, so there is no id worth pinning).

`--env` refuses, on **every** harness, any key the spawn sets on the tab itself --
`CODEX_HOME`, `CURSOR_CONFIG_DIR`, `PYTHONNOUSERSITE`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY`,
`HERD_WORKER`, `HERD_BRIEF`, `HERD_REPORT`, `ISOLATED_SESSION_GUARD_TRACE` and
`MURETAI_HERDR_AGENT` (which has `--muretai-agent`, with a name rule this door would skip).
The caller's entries are appended AFTER the spawn's own on `herdr tab create`, so a
duplicate key would leave it to herdr's dedup order which value the tab gets -- neither
pinned nor tested here, and the keys it would decide are the interpreter wall, the memory
switch and the config home. `MURETAI_BINDING_FILE` and `ISOLATED_SESSION_OWNER` are
deliberately not on that list: the spawn never sets the first, and the second is how a
test-author / implementer pair hands its worktree lock over. A WALLED worker always carries
an owner key -- behind wall v1 `ps` cannot run, so the process walk has no answer and
`iso_owner_pid` refuses rather than guess -- so when the caller passes none the spawn puts
the worker's own name there (one entry, never beside the caller's), hands over any lock
that key already owns, and its wall probe first runs `claim-worktree.sh` and
`assert-head.sh` under that key in a throwaway repository behind the wall; a wall under
which they fail stops the spawn.

## Briefs

- `briefs/worker.md` -- the generic one-shot brief (Dispatch, and anything that is not a test-author / implementer pair): the eight steps a worker takes (`stale.sh`; its OWN `ensure-worktree.sh "{{TITLE}}"`, so the worktree is the worker's and not the coordinator's; `assert-head.sh`; the task; the tests; `ledger.py new`; commit; `finish-worktree.sh` from the primary; the report to `~/.cache/muretai-herd/<name>/report.md`) and the rules (never push, no overrides, no full suite, never the generated files or `tools/test_times.json` / `tools/units.json`). A coordinator fills `TITLE`, `PLAN`, `UNIT`, `TESTS` and `TASK`.
- `briefs/test-author.md` -- the first session of a pair: the authority is the written requirement, not the implementer; functional AND refusal cases; the tests are supposed to fail; commit only tests; name every test path in the report. A coordinator fills `TITLE` and `TASK`.
- `briefs/implementer.md` -- the second session of a pair: read the test author's report; those paths are read-only; you may ADD a test but never edit, rename, skip or relax theirs. A coordinator fills `TITLE`, `PLAN`, `UNIT`, `TESTS`, `TASK`, `WORKTREE`, `BRANCH` and `TEST_AUTHOR_REPORT`.
- `briefs/dispatch-ticket.md` -- a Dispatch take: ticket fields as fenced DATA, the worktree dispatch-take already opened (`{{WORKTREE}}`/`{{BRANCH}}`; the worker runs no ensure-worktree.sh), then the same do / land steps, then deliver.

## Test-first: two sessions on one branch

An agent that implements a thing does not write the tests for it. A work item is two sessions on ONE branch, handed over with the same `ISOLATED_SESSION_OWNER` key.

A different agent reads the written requirement first -- the specification part and the plan item -- and writes both the functional cases and the refusal/security cases (`briefs/test-author.md`). Those tests are supposed to fail. The implementer then takes the same worktree and branch (`briefs/implementer.md`) and makes them pass, and may not edit the test files. A test the implementer wrote for its own code checks its own misreading, which is what this replaces.

Why one branch, not two landings: tests cannot land red on main because the landing gate runs the affected suite, so the pair share a branch instead of landing twice. The test author commits tests and stops without `finish-worktree.sh`. The implementer lands once, green.

The coordinator checks before landing: the diff of the test paths between the test author's commit and the branch tip is empty. That check is the only thing standing between this arrangement and self-grading, so it is named, not implied:

```bash
git diff <test-author-commit> HEAD -- <test paths from the report>
# must print nothing
```

```bash
bash .cursor/skills/isolated-session/scripts/herd-spawn.sh tests .cursor/skills/isolated-session/briefs/test-author.md \
  --var "TITLE=..." --var "TASK=$(cat ~/.cache/muretai-herd/briefs/<item>-requirement.md)"
# then, same worktree, same ISOLATED_SESSION_OWNER key:
bash .cursor/skills/isolated-session/scripts/herd-spawn.sh impl .cursor/skills/isolated-session/briefs/implementer.md \
  --env ISOLATED_SESSION_OWNER="<the test author's key>" \
  --var "TITLE=..." --var PLAN=host --var UNIT=tools --var "TESTS=tests/test_x.py" \
  --var "WORKTREE=/path/to/worktree" --var "BRANCH=feat/..." \
  --var "TEST_AUTHOR_REPORT=$HOME/.cache/muretai-herd/tests/report.md" \
  --var "TASK=$(cat ~/.cache/muretai-herd/briefs/<item>-requirement.md)"
```

**The hold passes at the spawn.** When `herd-spawn.sh` starts a worker with `--env ISOLATED_SESSION_OWNER=<key>`, every worktree lock of the cwd's repository whose owner is `<key>` is handed to that worker by name (`owner_worker=<name>` in the lock, the process fields emptied; stderr says which worktree). From that moment the author -- same key, another `HERD_WORKER` -- is refused like any second chat, and its SessionEnd no longer releases the lock. The worker's session binds its own process at its first guarded command (the hook, `assert-head.sh`, `claim-worktree.sh`, `ensure-worktree.sh`), so liveness follows the implementer, not the author; until then the lock is live by the key TTL. Only the named worker with that key binds it, and a symlinked lock or lock directory is never rewritten (`python3 tests/test_pair_lock_handover.py`). The implementer still never claims.

**The operator workaround** for a pair worktree that has no live holder anyway (the author ended before any hand-over, or the implementer died): in ONE terminal, without `ISOLATED_SESSION_OWNER` set, run `claim-worktree.sh <worktree>` and then `finish-worktree.sh <branch> <worktree>`. Both scripts find the owner by walking the process tree, so they only agree when they run in the same shell; a claim from one tab and a finish from another is refused as two sessions.

The reviewer a landing spawns is the same mechanism with the security-audit skill's `landing-review-brief.md`; `tools/security_weekly.sh` spawns the weekly hunt with its `weekly-audit-brief.md`. `python3 tests/test_herd_spawn.py` is the contract, against a herdr stub.

## Dispatch

Dispatch is orchestration across Herdrs: the job moves, the runtime stays yours. This skill is the Hand. After Bob's owner accepts a 1:1 coord ticket, `scripts/dispatch-take.sh --as <agent> --context <contextId> [--capacity-file PATH] [--primary DIR] [--room DID]` reads the thread from `operator_cli` JSON, refuses unless this DID accepted it, checks the local stance (`~/.muretai/dispatch/capacity`, `open` or `full`), checks Room `/mem` for a `taken-by` line (before "is this mine", so a third desk that was not the recipient still exits 4), writes `/remember note [task] <contextId> | taken-by=<did> lane=working at=<iso>`, opens the ticket's worktree itself (`ensure-worktree.sh "<title>"` in the resolved repo, under the owner key `dispatch:<worker>`; a re-take after a down herdr resumes it), and spawns a worker with `herd-spawn.sh` (worker profile) IN that worktree with `--env ISOLATED_SESSION_OWNER=<that key>`, so a walled worker's landing gate is the ticket's branch. `repo` is a name looked up in `~/.muretai/dispatch/repos` (`name=<path>`), or `--primary`. Ticket fields reach `briefs/dispatch-ticket.md` as fenced DATA through `--var` and are never a shell argument to anything else; the script never calls `herdr agent prompt`. Exit 0 spawned, 2 not accepted / not mine / missing key / unknown repo, 3 herdr down (prints the by-hand command), 4 stance full or already taken (prints who). `scripts/dispatch-capacity.sh open|full [reason]` writes the same capacity file the App's loopback writes. `python3 tests/test_dispatch_take.py` is the unit contract; `python3 tests/test_dispatch_v1.py` is the two-desk v1 fixture.

Once per machine, `scripts/dispatch-init.sh --as <agent> --repo <name>=<absolute path>` writes `agent` (`name=<agent>`) and a `<name>=<path>` line in `repos` under `$DISPATCH_DIR` (default `~/.muretai/dispatch`). Both files are mode 600, written by temp file and rename. Running it again leaves one line per name, and a new path replaces that name's line. It refuses a bad agent name (`[a-z][a-z0-9-]{0,31}`), a repository name with `=`, `/` or whitespace, a path that is not an existing absolute directory or that holds a control character, and a symlinked `agent` or `repos`; a refusal changes nothing. It does not write `room`. With a `room` file present, `finish-worktree.sh` takes the landing lease for the `repos` name that maps its primary: one signed HTTPS POST (`scripts/landing-lease.sh`) to the lease Durable Object in `worker/`, signed by the node's dedicated, unbound `lease=<name>` identity, at the url on the `endpoint=` line beside `node=` (or `[lease] url` in `LANDING_LEASE_CONFIG`, default `<dispatch dir>/lease.toml`); the release carries the epoch the take was granted. `LANDING_LEASE=off` or `APPL_LEASE=off` is the break-glass (`LEASE=off (break-glass)`). When either is missing, it refuses before anything moves and prints the `dispatch-init.sh` command to run. After the hand-off push, it holds the lease until the publisher's status file (`LANDING_PUBLISHER_STATUS`, else `<state>/status/<name>.txt`) shows a `when=` newer than the push, the pushed `handoff=`, and `result=published` or `up-to-date` (`PUBLISH=<result>`). If none appears within `LANDING_PUBLISH_WAIT_S` seconds (default 300), it prints `PUBLISH=timeout`. If the publisher answers "not a fast-forward", the landing reads origin again, rebases local BASE onto it, re-runs the tests, the lint and the ledger, and re-pushes, at most twice. After that, or after any failed round, the receipt says `HANDOFF=held <reason>` and the exit is still 0. `python3 tests/test_landing_publish_wait.py` is the contract.

## Copies in other repositories

This skill's home is the core trunk. Any other repository carries a pinned copy: `scripts/vendor.sh pull` brings the scripts, this file and the contract test over from `${MURETAI_CORE:-~/muretai-trunk}` and writes `VENDOR.json`; `scripts/vendor.sh check` holds the copy to that pin with no core checkout present. What is copied is the explicit `FILES` list in `vendor.sh`; both `pull` and `check` refuse when a listed script reaches a sibling (`$here/<name>`, a sourced `$(dirname ...)/<name>`, Python `HERE / "<name>"`), directly or through several hops, that the list or the pin leaves out. `pull` also refuses a symlinked source and a `..` or absolute entry before it writes anything. The APPL `appl-*.sh` scripts are not vendored (ISSUE(herd-spawn-names-unvendored-appl-scripts)). Never patch a copy -- fix the home and pull again. The script judges the repository by where it lives, so the first pull is a bootstrap: copy `scripts/vendor.sh` and `scripts/lib.sh` into the new repository's `.cursor/skills/isolated-session/scripts/`, then run that copy's `vendor.sh pull`. The home's scripts also run against any other checkout you `cd` into -- that is how the first session in a repository without the skill is opened.

## Never

Two chats in the same folder. Commit on main. Force-push shared branches. Reuse another session's branch. Leave a finished session unmerged. Open a draft PR instead of merging. Push BASE from a session. Land design in a dev session, or dev in a design session, without saying why.
